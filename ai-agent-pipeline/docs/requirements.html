개발 에이전트

역할

유심히 볼 부분

공유 사용량 풀 충돌 위험을 피하기 위해 동시 병렬 대신 순차 실행으로 확정.

1 · DB
스키마 우선 확정
2 · BACKEND
DB 스키마 기준 API 구현
3 · FRONTEND
API 스펙 기준 연동 구현

⚠ 선행 단계인 PL/기술리더가 제외되어 인터페이스 계약 없이 개발이 진행됩니다.

테스트 실패 시, 같은 오류라도 원인에 따라 되돌아가야 할 단계가 다릅니다. PM 에이전트가 원인을 먼저 분류합니다.

PM의 실패 분류 로직

원인 분류 없이 계속 개발 단계에서만 재시도하면, 고칠 수 없는 설계·요구사항 문제를 영원히 구현 버그처럼 다루게 됩니다.

테스트 실패 감지
구현 버그→ 개발 에이전트로 재전송 (최대 N회 재시도)
설계 결함→ 설계 · PL 에이전트로 되돌림, 인터페이스 계약 재검토
요구사항 모호 / 오류→ 기획 에이전트로 되돌림, 사람 승인 재요청

자율 해결 우선 원칙

확정 · 방향성

사람에게 묻는 것은 최소화하고, 에이전트들끼리 최대한 자율적으로 해결하는 것을 기본값으로 합니다. 다만 완전히 사람 개입을 없애는 게 아니라, 이슈를 3단계로 나눠 정말 되돌릴 수 없거나 리스크가 큰 경우만 실시간으로 사람에게 갑니다.

티어해당 이슈처리 방식
TIER 1 · 완전 자율 구현 버그, 코드 스타일, 컨벤션 위반, 일반적인 기술 이슈 사람에게 묻지 않고 에이전트 간 재시도 루프로 즉시 해결 (기존 최대 재시도 상한 적용)
TIER 2 · 가정 후 진행 + 기록 설계 해석의 모호함, 우선순위 판단, 이미 승인된 설계 범위 내 조정 에이전트가 가장 합리적인 가정으로 진행하고 assumptions에 기록 → 사람에게 실시간으로 묻지 않고, 다음 정기 체크포인트(승인①②③)에서 일괄 검토
TIER 3 · 즉시 확인 필수 이미 확정된 요구사항 자체를 뒤집는 경우, 비가역적 변경, 보안 · 법적 리스크, 비용/일정에 큰 영향 이 경우에만 CTO를 통해 사람에게 즉시 에스컬레이션 (예외적으로 최소화된 개입)

특정 단계에 속하지 않고 파이프라인 전체에 적용되는 원칙입니다. 우선순위 순으로 정렬했습니다.

최우선

초기 설계

체크포인트 세분화

현재 단위는 "단계(stage)" 단위인데, 한 단계 안에서도 수십 번의 파일 수정이 있을 수 있음. 단계 도중 한도에 걸렸을 때 재개 지점을 더 세밀하게(파일 단위 등) 기록할지 결정 필요.

초기 설계

원자적 파일 쓰기

공유 상태 파일(pipeline_status.json)은 PM만 쓰게 하고, temp → rename 방식의 원자적 쓰기로 손상 방지 필요.

초기 설계

히스토리 압축 전략

초기 설계

에이전트 스킵 시 의존성 검증

사용자가 특정 에이전트를 제외했을 때, 다음 단계가 필요한 입력을 못 받는 상황(예: 코드 리뷰 없이 테스트 진행)을 PM이 실행 전에 검증해야 함. 01번 탭 프로토타입은 선행 단계 제외 시 경고만 표시하지만, 실제 프로그램에서는 "경고 후 진행" 허용 범위와 "무조건 차단" 범위를 구분해서 정의 필요.

초기 설계

제외된 에이전트의 산출물 대체

예: 보안 검토를 제외하면 요구사항 추적 매트릭스에서 그 항목을 "미실시"로 명시할지, 아니면 완전히 생략할지 — 고객사 납품 시 책임 소재와 직결되므로 정책 확정 필요.

초기 설계

CTO 상태 요약 카드 스펙

CTO가 원본 히스토리 대신 참고할 "상태 요약 카드"의 필드 구성(status/summary/open_issues 등)과 갱신 시점(매 턴 vs 단계 완료 시)을 확정해야 함. 이게 부실하면 CTO가 부정확한 답을 하거나, 결국 원본을 다시 다 읽게 되어 05번 탭에서 설계한 경량화 효과가 사라짐.

초기 검증 필수

JSONL 세션 로그 실제 필드 형식 확인

~/.claude/projects/**/*.jsonl의 message.usage.input_tokens/output_tokens 등 필드 경로가 실제 로컬 파일과 일치하는지 확인 필요. Claude Code 버전에 따라 구조가 다를 수 있어 방어적으로 파싱해야 함 (engine/lib/usageMonitor.js — 대시보드는 dashboard/lib/engineBridge.ts로 이 파일을 그대로 재사용).

참고

OAuth usage API (미채택)

조사 중 Claude Code가 내부적으로 쓰는 것으로 보이는 비공식 엔드포인트(api.anthropic.com/api/oauth/usage)를 로컬 저장 토큰으로 직접 호출해 5시간/주간 한도 %까지 얻는 방법도 발견됨. 다만 비공식·미문서화 API라 버전 변경에 취약해 채택하지 않음 — 필요하면 이 방식으로 확장 가능.

초기 설계

티어별 구체적 임계값

02번 탭의 "자율 해결 우선 원칙"으로 큰 틀(Tier 1/2/3)은 확정했으나, Tier 1 재시도 횟수, Tier 2 "합리적 가정"의 구체적 기준, Tier 3 "비가역적 변경"의 판단 규칙은 아직 수치·규칙으로 확정되지 않음. 이 기준이 느슨하면 잘못된 가정이 쌓이고, 너무 엄격하면 Tier 2가 사실상 Tier 3처럼 작동해 사람 개입 최소화 원칙이 무색해짐.

이 문서로 설계를 정리한 뒤 실제 코드(ai-agent-pipeline 프로젝트)로 옮기면서, 사용해보고 나서 드러난 문제를 그때그때 고친 내역입니다. 설계 문서와 실제 구현이 어긋나지 않도록 여기에 모아둡니다.
